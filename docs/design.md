# Design decisions

## 1. The image proves the modules

The ledger and network modules are not installed from a gallery; the Modules task copies them from the sibling
repos into `build/modules/` and the Dockerfile copies that into the image's PowerShell module path. The end-to-end
run therefore tests exactly the module source on disk, inside the runtime it ships in (Linux, PowerShell 7.4,
non-root), not just on the developer's Windows host. A module change is proven when this repo's build goes green.

## 2. Secrets by mount only

Nothing secret is in the image or in git. `ANTHROPIC_API_KEY` is optional and arrives at run time from a
gitignored `.env` (or the shell) via Compose interpolation. The ledger's HMAC key is generated by the `ledger`
keeper onto the ledger volume, which the agent never mounts. The mitmproxy CA is generated by the sidecar onto its own volume and mounted read-only into the
agent. `.dockerignore` excludes `.env` and `artifacts/` so neither can leak into a build context.

## 3. Ledger on a volume the host keeps, written by a keeper the agent cannot reach

The agent writes unsigned entries to the `spool` volume; the `ledger` container (Claude.Agent.Ledger's keeper,
built from `ledger.Dockerfile`) chains them into the `ledger` volume with a key only it holds. The agent mounts
`spool` and never `ledger`; the keeper runs with `network_mode: none`. See Claude.Agent.Ledger design 3.

`ledger` is a named volume. `docker compose down` keeps it; only `Invoke-Build Clean` removes it. Runs
accumulate entries on one continuous chain, so the history across runs is verifiable, not just the last run.
Smoke waits for the keeper to drain the spool, stops it (SIGTERM, one final flush, must exit 0), then copies
the volume out (`docker cp` from a created-but-never-started container), so verification never depends on any
container being alive or honest at read time. It also asserts that the agent image contains no `key.bin` and
the agent container has no `/ledger` mount.

## 4. A sidecar the agent cannot reach

Traffic is recorded by the `mitm` container from Claude.Agent.Network, and it is the agent's only way out: the
agent is on the internal `inside` network alone, `mitm` bridges `inside` and `outside`, and the proxy env is a
convenience (Claude.Agent.Network design 1). The entrypoint's `agent.egress-check` proves a direct request
fails before every run, and the run aborts if it does not. The agent mounts only the CA (read-only);
the `capture` volume is mounted into `mitm` and into host-started converter containers, never into `agent`.
The agent starts as root only long enough to install the CA into the system store, then re-executes itself as
user `agent` (uid 10001, distinct from mitmproxy's 1000 so it cannot read the CA private key).

## 5. Smoke writes a report, Pester asserts the report

The Smoke task gathers facts (ledger verified, entry kinds of the last run, probe/run outcome, flows to
`api.anthropic.com`, image size) into `artifacts/smoke-report.json`, and fails fast on the essentials. Pester
then asserts the same facts from the report. The report is the durable, diffable record of a run; the Pester
result is the pass/fail record in a format CI already understands. Keeping Docker work out of Pester means the
tests are fast and can be re-run against a saved report.

## 6. A tool policy baked at build, enforced by hooks, decided in the ledger

What the agent may do with its tools is a file, not a prompt: `/opt/agent/policy/policy.json`, generated in the
image build by Claude.Agent.Policy's `New-Policy` from the vendored Graph.Emitter.FileSystem ontology (plus the
module's own tool ontology) and checked by `Test-Policy` before the layer is committed. A policy that does not
validate fails the image build. The policy, the hooks and the settings fragment are root-owned and read-only,
so the agent (uid 10001) can run the hooks but cannot change them or what they enforce.

The ontology is vendored, not read from `../Graph.Emitter.FileSystem`, so the image does not depend on a fourth
checkout and a change to the emitter's actions reaches the agent only when someone recopies it here (Modules
warns when they differ).

The hooks go into `~/.claude/settings.json` at container start (Claude.Agent.Policy design 6 for why not
managed settings yet). Smoke runs a prompt that reads, writes under `/work` and deletes, and requires the
ledger to hold allow, allow, deny in that order and the file to survive, checked by `docker cp` from the
stopped container rather than by anything the agent reported. Which tool claude uses to delete is left to it,
and nothing in the prompt or the deny message tells it not to try again, so `policy.afterDeny` in the report
records whether it honoured the deny.

## 7. Alerts read the copied ledger on the host, and write a layer

After Smoke has verified the ledger and deleted the key from the host copy, the Alerts task runs
Claude.Agent.Alerts over `artifacts/ledger/ledger.jsonl` (Claude.Agent.Alerts design 1: read-only, keyless,
never on the agent network). The module and GraphNode are copied to `build/host-modules/`, not `build/modules/`:
the Dockerfile copies `build/modules/` wholesale into the agent image, and a reader of the ledger has no
business in the image whose behaviour it judges. `.dockerignore` keeps `build/host-modules` out of every build
context.

Alerts covers the last run only (`-FromSeq` = seq of the last `agent.egress-check`), the same unit Smoke
reports, because the ledger volume accumulates runs until Clean. The layer goes to
`artifacts/alerts/<utcStamp>.graph.json` for the portal; the report gets a summary and the error findings.

The assertion is exact: on a `claude -p` run, one error, and it is the `policy.deny` of the prompt's delete.
Any other error (a seq gap, a rejected spool line, a non-zero exit, a denied call that ran) means a broken
run. Warnings (witnessed shell) do not fail the build; they are there to be read.

## 8. The keeper starts first, and the agent waits until it has

Claude.Agent.Ledger design 4: on start, the keeper raises the spool's seq counter to the last seq in the
ledger, so a lost counter (spool volume recreated while the ledger volume is kept, or `seq` deleted) does not
restart the writer at 1. That sync is only safe if it happens before the agent's first write; a writer that
appends first takes seq 1 again and every later run fails `seq-gap`. Keeper-starts-first is what makes the
sync safe.

Compose enforces it. `agent` already had `depends_on: ledger: condition: service_started`, but that only orders
container start: the keeper's pwsh could still be importing its module when the agent spooled
`agent.egress-check`. Now `ledger` has a healthcheck, `test -f /spool/seq`, and `agent` waits for
`service_healthy`. The file is the right signal because the sync always writes it when it is missing, and
missing is exactly the dangerous case; when it is present (the normal case) the writer continues from it,
which is already correct. `Invoke-Build Clean` drops spool and ledger together, so a fresh pair starts at 0
on both sides.

Not covered: a `seq` file that is present but lower than the ledger (edited by hand). The keeper still raises
it on start, but the healthcheck does not wait for that. Nothing in this repo writes one.

## 9. One reserved host port, published by nothing yet; one project name, passed every time

Nothing in this stack needs to be reached from the host: the agent talks out through `mitm`, the keeper has no
network, and the host reads volumes by copying them out. So no service publishes a host port. One is reserved,
`CLAUDE_AGENT_PORT` (8300), for an Alerts/Ledger API when one exists, so the portal and the docs can name it now
and nothing else claims it later. `compose.yaml` carries it as a commented `ports:` line on the keeper, bound to
127.0.0.1; switching it on also means giving the keeper a network, which reopens design 3 and is a decision of
its own. Smoke fails if any host port other than the reserved one is published, looking both at the resolved
compose config (`ports`, or `network_mode: host`) and at the port bindings of the project's containers, running
or stopped. Status is stricter and fails if any host port is published at all, the reserved one included,
because nothing is meant to publish it yet.

The project name, `COMPOSE_PROJECT_NAME` (default `claude-agent-dev`), decides the container, network and volume
names the build inspects (`<project>_inside`, `<project>_ledger`, ...). If the build and Compose disagreed, the
build would check one project's volumes while Compose ran another, so `.build.ps1` resolves the name once and
passes it as `--project-name` on every `docker compose` call, and exports both settings for interpolation.

For these two settings `.env` wins over the environment, then the defaults in `.env.example`. That is the
opposite of Compose's own order (shell over `.env`), and deliberate: they describe the checkout, so a stray
shell variable should not quietly move the build to another project. Credentials keep Compose's order
(Test-CredentialPresent), because there the shell overriding `.env` is the documented way to run without a file.

## 10. The run itself is a layer too

`smoke-report.json` is this repo's own record; the portal reads Graph.Node envelopes. So after each build the
Runs task also writes the run as a run-report layer, in the shape Graph's run-report skill defines (copied into
`.claude/skills/run-report`, read-only here): `artifacts/runs/<layer stamp>.graph.json`, a copy at
`artifacts/runs/latest.graph.json` (a copy, not a link, as for the alerts layer), and the
run-report `ontology.yaml` beside them. `smoke-report.json` is untouched; the layer is derived from it.

What goes where:

| Kind | From |
| --- | --- |
| Run | repo, the invocation, start (Invoke-Build's own start) and finish, tasks completed, Pester totals, image name and size, auth path, project, `alertsLayer` |
| Finding | each Finding in the alerts layer (the rule's severity), then the egress check (info when blocked, error otherwise), then the published-port check (info, or error on a stray port) |
| Decision | the auth path, and for each image whether `docker compose build` reused it from cache, rebuilt it, or was not run |
| NotRun | each chain task this invocation did not run, and the Pester tests skipped for the other run path |
| Touched | every file under `artifacts/` and, when Modules ran, `build/modules`, `build/policy`, `build/host-modules`; never staged, both are gitignored |

Edges follow the ontology: Run `reports` Finding, Decision and NotRun, and Run `touched` Touched (the ontology
has no `reports` edge to Touched).

Runs is the last task, after Pester, not straight after Smoke: the ontology requires the Run's Pester totals, and
the Run links the alerts layer, which the Alerts task writes after Smoke. Pester leaves its totals in
`artifacts/pester.json`. The cost: when an earlier task fails, the build stops and no run report is written for that
build. The Pester tests cannot read a layer written after them, so `tests/RunReport.Tests.ps1` builds one in a
scratch directory from the same run's artifacts with the same function (`tools/RunReport.ps1`). The Runs task
itself fails unless `graphnode validate --ontology` prints `[]` for both files.

Cross-link without an edge: the Run's `properties.alertsLayer` is the alerts layer's `layer` stamp. An edge to a
Finding in the alerts layer would dangle in this envelope (and `alert:` belongs to Claude.Agent.Alerts), so the
join is left to the portal, which mounts both layers. The envelope's `version` is the run-report ontology's
(0.2.1), because the module it declares is Graph.RunReport, not Claude.Agent.

## 11. Up draws the run on the portal, and replaces a stack that is already up

A run should be visible when Up finishes, not after the whole chain. So Up ends by exporting the ledger with
Graph.Emitter.Agent's `Export-AgentRunGraph` (`-Strict`, so an error finding such as a broken chain or a denied
call that ran fails Up) into `artifacts/layers/<stamp>.runs.graph.json`, posting the folder `artifacts/layers` (made absolute) to Portal's
`POST /api/layers` on `http://127.0.0.1:8200` as layer `agent-runs`, and printing one line,
`agent run <stamp> at http://127.0.0.1:8200/ (<n> nodes, <m> edges)`. The layer is posted by path, not as a body,
because Portal resolves the envelope's relative `ontology.yaml` only beside a file. The path is the folder, not
the new file: Portal mounts a folder's newest `*.graph.json`, and since Portal 0.3.5 records a mount by path as a
`ui:mount:<name>` node that an approval saves and a restart mounts again, so with the folder a saved mount
follows the latest run instead of the one that happened to be approved. A portal that is not listening
is not a build failure: Up prints the layer path and `portal not up on 8200`. A portal that answers and refuses the
layer is one. `-NoPortal` skips the export and the POST.

The ledger is still copied out in Smoke, after the keeper has stopped; Up needs it earlier. Up waits for the keeper
to drain the spool, then copies `ledger.jsonl` alone off the volume (never `key.bin`, which only Smoke's
`Test-Ledger` needs and then deletes). Nothing is written after the agent exits, so that copy is the whole run.
The layer holds every run in the ledger, not only the last, because the ledger volume keeps them all.

`policy.json` is copied out of the image before the run, byte for byte, to `artifacts/policy.json`: the emitter
gives a decision its rule text only when the file's SHA-256 is the run's `agent.start` `policySha256`. Smoke now
clears `artifacts/` except Up's three outputs (`policy.json`, `layers/`, `up.json`), which belong to the same run.

The emitter is imported from `../Graph.Emitter.Agent`, not copied into `build/host-modules`: it finds its ontology
and Graph.Node relative to its own checkout.

Snapshots: from Claude.Agent.Ledger 0.2.4 the entrypoint spools `agent.snapshot` (`Get-AgentSnapshot`) right after
`agent.egress-check`, whatever that found, and again just before `agent.stop`. A container cannot read its own image
digest, so Up hands the image id in as `CLAUDE_AGENT_IMAGE_DIGEST`. Graph.Emitter.Agent 0.1.2 predates the kind and
reports each snapshot as an `unknown-kind` info finding; that is expected until it learns it.

Replace: Up used to `up -d --force-recreate` over whatever was there. Now, the shape of Portal's Up, a stack that
is up (any container of the project running) is brought down, Up waits up to 30 s for its containers to go, brings
it up and logs `replaced <old stamp> with <new stamp>`. A stack's stamp is when its agent container started, else
its earliest running container. `-NoReplace` throws instead and touches nothing. Everything Up did is recorded in
`artifacts/up.json`, which `tests/Up.Tests.ps1` reads.
